## Quick Mod Features
### Remove location from quick content and move it to the map
In the map, there should be a toggle (edit mode) which enables a different sort of interaction. 
in edit mode, you can drag nodes around instead of travelling to them
clicking on a node or edge opens up the settings for that node or edge
clicking on an empty location prompts to add a new location at that x,y coordinate
add directed edge: perhaps another button that allows selecting two nodes to connect them in the forward direction. 
add node: Clicking on an empty location/background

### Automatic adding of features
When creating a new location, add 2 checkboxs to auto create travel action to and from current location
When creating an entity, add a checkbox to add the entity to the current location.
### Create a tutorial guide entity. 
Create a tutorial guide entity and add it to wayside crossing
Create a new common talk action which spawns the current tutorial guide dialogue. 
Remove the dialogue from wayside crossing

### Dialogue should show a node/edge graph
Dialogue tree, with root node, the ability to create edges between nodes. 
Clicking on an edge allows editing of the dialogue options, adding requirements, etc
Clicking on a node allows you to edit the dialogue. 
Dialogue editing should be in english (or the chosen locale), keys should be autogenerated. 
The goal is to make dialogue editing easy. 
### Work in 'en' with autogenerated ids
Currently, there are locale warnings every time any new prototype is added. Ideally, development works in a chosen localization so that you don't need to go back into the mod to update locale. 
### Durability and hardening pass on local mod development
malicious hardening such that the game is robust enough to handle real world development work by people who are not necessarily familiar with the code base. 
### Unify validation and local mod edits so that no matter where the edit occurs, it uses the same logic and doesn't break or require custom code. 
### Default localization for common actions.
Each travel action doesn't need to have its own unique localization. Ideally you can define something like 'Travelling to {location}' with the option for a manual override that the validation layer doesn't require. 
Or for example: If there are 10 different types of bones, it would be nicer to say: 'You bury the '{bone.name}.' instead of having 10 different localizations that are functionally identical.
