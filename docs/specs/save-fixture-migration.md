# save-fixture-migration

## Deliverable

`loadSave` accepts one version and rejects every other, and there is no migration. So the cost of
bumping `SAVE_VERSION` is not the bump — it is that every `# save` fixture in shipped content has to
be regenerated by replaying its whole route live, whether or not the bump touched anything the
fixture holds. Measured on this branch: setting `SAVE_VERSION = 7` and changing nothing else reddens
eight tests across four files, and every one of them fails on the version stamp alone, with a body
that was still perfectly valid.

Four save-breaking branches are queued, and saves are sparse diffs against `initialState`, so a
field sitting at its default is absent rather than present-and-default. That decides how much work
each bump really is. No fixture in shipped content carries `activeBuffs`, `equipped`, `activeAction`,
`player` or `resourceRateRemainders` — so `result-application-seam`, which makes `activeBuffs`
actor-scoped, and `buffs-generalized`, which holds buffs per actor, change no field any fixture
holds. Their fixtures need a version restamp and nothing else, and today that restamp is bought by
replaying a route to re-record a byte-identical body. `first-class-modals` and
`items-mods-and-crafting` do move fields the fixtures carry — `pendingModal` in `miki-route-end`,
`inventory` in two — and each is a one-line transform.

This branch builds the one-shot command that does the restamp, applies the bumping branch's single
transform when the shape did move, and is honest about the half it cannot do. Rewriting a fixture's
shape makes it *loadable*; it does not make it *true*. `miki-route-end` pins `time`, `rng` and a
`resources` entry that finding `dsl-load-path-2026-07-30-pass2-h1` says is already wrong, and a
shape migration would carry that forward faithfully. When a branch changes behaviour, the recording
has to be re-recorded, and the command's job is to say so by name rather than to paper over it.

Proof:

- [c1] The command rewrites the body of every `# save` section in `content/**/*.dsl`, and leaves
  every other byte of every file it touches unchanged — comments, blank lines, section order, and
  the sections either side. The six-line note above `dresser-trinket` is where its author put it
  after the command runs.
  proof: vitest scripts/migrate-saves.test.ts
- [c2] Running it twice is running it once. A fixture already stamped `SAVE_VERSION` is skipped
  rather than transformed a second time, so a re-run changes no bytes and a mis-run cannot compound.
  proof: vitest scripts/migrate-saves.test.ts
- [c3] Nothing is written until everything validates. Each rewritten body is checked by loading it
  against the real registry; if any fixture fails, the command writes no file at all and exits
  non-zero.
  proof: vitest scripts/migrate-saves.test.ts
- [c4] A bump has to state what it did to the shape. The command refuses to run with an unset
  transform, so "this bump moved no field" is declared rather than indistinguishable from "I forgot
  to write one".
  proof: vitest scripts/migrate-saves.test.ts
- [c5] Inputs and recordings are not confused. The command reads `# test` sections to classify each
  fixture as an input (`load:`) or a recording (`expect:`), names every recording it rewrote as
  needing regeneration with `/create-valid-test`, and reports any fixture no test references.
  proof: vitest scripts/migrate-saves.test.ts
- [c6] The migration surface is content only. Bumping `SAVE_VERSION` alone reddens shipped-content
  fixture tests and nothing else, and every one of them goes green once `npm run migrate-saves`
  restamps content, with no source change. That property is the clause; the count moves with the
  test set, as this branch's own later commits proved by moving it. Measured on the branch's final
  state: five failures across two files — three in `src/runtime/integration.test.ts` replaying the
  shipped fixtures, and two in `scripts/migrate-saves.test.ts` asserting that shipped content is
  already at `SAVE_VERSION`. The eight across four measured before this branch included the
  `{"version":6}` literals in `save.test.ts`, `session.test.ts` and `play-cli.test.ts`, which no
  content migration could reach; they are built from `SAVE_VERSION` now, so a bump does not reach
  them at all.
  proof: npm test

## Decisions

- **Shape and behaviour are not substitutes, and the command says which one it did.** This is the
  distinction the whole task rests on, so it is not left to prose in an evidence field: `load:`
  fixtures are inputs and a shape migration finishes them, `expect:` fixtures are recordings of a
  replay and a shape migration only makes them loadable. Two of the three fixtures in shipped
  content are recordings. c5 is what makes the command state that at the moment it matters.
- **A tool, not a ladder — the transform is disposable but its history is not.** One named, exported,
  pure function in `scripts/migrate-saves.ts`, overwritten by the next bump. Nothing accumulates,
  no old version stays loadable, and a transform that turns out wrong is deleted rather than
  maintained. Retaining rungs would put untested code with no caller in `src/runtime` and soften
  exactly the promise that makes this cheap. Keeping it one exported function costs nothing and
  makes `git log -p scripts/migrate-saves.ts` the ladder's history when `save-migration-system`
  comes to build one.
- **This branch is retired by the ladder, not maintained beside it.** Once `loadSave` migrates an
  old save forward on read, a fixture can stay at its authored version forever and this command has
  no job left. `save-migration-system` inherits the obligation to delete `scripts/migrate-saves.ts`
  rather than keep two answers to one question. The split stands anyway: a ladder maintained while
  the shape is still moving is four branches of rungs kept correct for no live player.
- **No write on `src/runtime/save.ts`.** `SAVE_VERSION` is already exported and `scripts` sits above
  `runtime`, so the command imports what it needs and adds no seam. Four open specs name that file;
  taking a grant on it to add nothing would collide with all of them for free. c3 validates by
  loading rather than by re-stating `checkSave`'s field table, which is both a stronger check —
  it catches pruning too — and the reason no export is needed.
- **A surgical line rewrite, not a serialize round trip.** `serialize.ts` can already emit a `# save`
  section, but re-serializing a whole content file would relocate or drop the hand-written comments
  above the fixtures, which are the only record of why those routes pin what they pin. The command
  replaces the one body line in place.
- **The new file needs an owner before it needs a test.** `scripts/migrate-saves.ts` and its test are
  added to Testing procedure's `paths` in `docs/audits/systems.json`; the partition is the one
  condition `npm run audit-status` fails on, and an unowned tracked file breaks it.
- **The test-source literals leave the surface permanently rather than joining the tool's scope.**
  Building them from `SAVE_VERSION` is a smaller fix than teaching a script to edit TypeScript, and
  it removes them from every future bump rather than handling them at each one.
  `src/content/serialize.test.ts` keeps its literal: it is a parse/serialize round trip that never
  checks the version, it did not fail under the measured bump, and `content` cannot import from
  `runtime`.

## Open questions

- Whether the transform is applied per-fixture or handed the whole set is left to the first slice.
  c4 fixes that it must be declared, not what it receives.
- Whether the command discovers content files by glob or by the module manifest is the worker's
  call once the region is read; c1 fixes the set it must cover, which is every `# save` in content.
