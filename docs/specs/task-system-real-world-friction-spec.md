# task-system-real-world-friction-spec

## Deliverable

The task system becomes a reliable swarm coordination surface under real
multi-agent use. A planner can see what is blocked, in flight, and next; a
worker can know which test proves a promised clause; an auditor can verify the
branch without reconstructing the diff by hand; and routine task commands stop
creating noisy or stale state.

This spec is written as an implementation plan, not as a bootstrap exercise.
Do not require the task system to manage this branch until the store serializer
and spec binding work land. After that point, attach the folded task ids listed
below if doing so produces a small, reviewable `docs/tasks.jsonl` diff.

Proof:

- [c1] Proof clauses can name executable proof targets, and
  `tasks check --merge` fails when a named target is missing, skipped, or
  failing. At minimum, support Vitest test-file-plus-test-name targets and a
  command target for proof that is not a single test.
- [c2] `tasks done` records the commit that closed a task, warns when its store
  write is uncommitted, and `tasks check` reports task state that exists only in
  the working tree or points at a closing commit not reachable from `HEAD`.
- [c3] The store supports an `in-progress` state with `tasks start <id>` and
  `tasks stop <id>`, and `tasks list`, `tasks next`, `tasks show`, `tasks
  handoff`, and `tasks spec show` surface in-flight work without treating it as
  complete.
- [c4] Spec identity and proof identity cannot be changed accidentally: a branch
  rename cannot make the merge gate not-applicable while open members exist, a
  never-amended spec has an opening freeze baseline, top-level proof clauses are
  the only clauses that receive ids, and a retired clause id is never reused for
  a new clause that has not been audited.
- [c5] The auditor path is explicit and repeatable: `tasks audit-prompt <spec>`
  prints a recommended auditor prompt containing the diff range, proof clauses,
  member tasks, relevant files, proof targets, required commands, and a mutation
  testing instruction for pure logic/API proofs.
- [c6] The command surface removes the real friction observed in
  `combat-continuation-runtime`: `tasks --help` works, `tasks spec <slug>` means
  `tasks spec show <slug>`, `tasks spec show --order` topologically sorts by
  `requires`, `tasks next` is concise by default with `--full` for evidence, and
  `tasks search` names the matching field.
- [c7] The commit contract no longer requires `Next:` on every commit. The hook
  still requires a useful body for non-exempt commits, accepts optional `Next:`
  as an extra breadcrumb, and the installed hook uses the repo-local `tsx`
  launcher before falling back to `npx`.
- [c8] The testing and gate cost is paid where it buys reliability: most
  `scripts/tasks.test.ts` command-semantics cases run in-process through
  exported `run(argv)`, only subprocess/Git-history smoke cases stay
  out-of-process, `noUnusedLocals` and `noUnusedParameters` are enabled, and
  `npm test`, `npx tsc --noEmit`, `npm run layer-check`, `npm run tasks --
  check`, and `npm run tasks -- check --merge --spec
  task-system-real-world-friction-spec` pass.

## Decisions

### Tests before implementation

Yes, by system rule for non-UI work. For pure domain logic, task-store logic,
spec parsing, merge-gate checks, command parsers, and API-like helpers, workers
should write or update failing tests before the implementation. The task system
is exactly the kind of code where TDD pays: most defects here were false
completion claims or edge-case state transitions that a focused test can pin.

UI work remains different. For interactive UI, write implementation first when
needed to discover the shape, then add tests or smoke checks around the settled
behavior. This branch is not UI work.

### `Next:` commit trailers

Do not require `Next:` on every commit. The trailer modeled a single agent's
session handoff, but a swarm has multiple leaves in flight and the spec/store
already know the next task. A required trailer becomes stale almost immediately
and duplicates the member list.

Keep commit bodies mandatory. Keep `Next:` optional and display it in
`tasks handoff` only as a recent breadcrumb. If a session deliberately ends with
a helpful `Next:`, the tool may show it, but no gate should treat it as the
source of truth.

### Auditor support

Auditors need a prompt and executable proof, not more prose. The recommended
auditor prompt should be generated by the tool so it cannot drift from the
current branch:

```text
You are auditing <spec> on branch <branch>.
Read the spec deliverable, the latest audit pass if any, and the diff
<base>..<head>. Verify each proof clause independently. For every clause with a
proof target, confirm the target exists and fails under a meaningful mutation or
reproduction before accepting it as proof. For pure domain logic and API layers,
prefer mutation testing: temporarily remove, invert, or scale the behavior the
test claims to prove and confirm the named proof fails for the right reason.
For UI work, inspect behavior and add/run smoke tests after the implementation
has settled.

Report:
- clause verdicts as met/unmet with one-sentence evidence;
- findings with severity, system, files, evidence, and deliverable;
- any proof target that is missing, skipped, too broad, or non-specific.
Do not promote pass-2+ findings. Do not treat green tests as proof unless they
are tied to the clause they discharge.
```

Mutation testing should not mean a full mutation-testing framework here. It
means an auditor actively perturbs the exact behavior under review and records
whether the proof target catches it. That was the difference between "green
suite" and "actually proven" during the combat continuation branch.

## Implementation Slices

### Slice 1 - Canonical Store and Fast Tests

Files to read first:

- `scripts/lib/taskStore.ts`
- `scripts/lib/taskStore.test.ts`
- `scripts/tasks.test.ts`
- `docs/tasks.jsonl`

Instructions:

- Write tests first for canonical key order, malformed JSONL/conflict-marker
  reporting with path and line number, and shape validation for required fields.
- Add a single serializer path that renders every task field in the same order.
  Loading an old line and saving it must not move fields except to canonicalize
  once.
- Convert ordinary command-semantics tests to call `run(argv)` in-process with
  captured stdout/stderr/exitCode. Keep subprocess coverage for process wiring,
  hook invocation, and real Git-history behavior.
- Re-run the task tests before and after the conversion and record wall-clock
  improvement in the audit evidence.

Acceptance:

- The key-order finding produces a small, understandable diff.
- A malformed line in `docs/tasks.jsonl` fails `tasks check` with a check error,
  not an uncaught stack trace.
- The suite keeps a few subprocess smoke tests but no longer cold-starts `tsx`
  for most command semantics.

### Slice 2 - Spec Identity, Freeze, and Clause IDs

Files to read first:

- `scripts/lib/specDoc.ts`
- `scripts/lib/specDoc.test.ts`
- `scripts/lib/mergeGate.ts`
- `scripts/lib/mergeGate.test.ts`
- `scripts/tasks.ts`

Instructions:

- Write failing tests first for: unamended spec drift, branch rename making the
  gate not-applicable, retired clause id reuse, nested sub-bullets receiving ids,
  and directory entries under `docs/specs`.
- Give specs an opening freeze baseline. Cheapest accepted shape is amendment
  zero created by `tasks spec new` once the deliverable is filled through an
  explicit `tasks spec freeze <slug>` command, or a first-class baseline section
  that does not duplicate the live deliverable as a normal amendment. Do not
  make the user run `spec amend` on an unchanged deliverable.
- Change merge-gate resolution so a branch with open spec members cannot pass as
  not-applicable merely because the branch name changed.
- Ensure only top-level `Proof:` bullets are proof clauses. Indented bullets are
  prose.
- Track retired clause ids, or otherwise compare current clause text identity
  against the latest audited/frozen identity, so a new clause cannot inherit an
  old `met` verdict.
- Make the spec scan skip non-regular files and report parse errors as check
  issues.

Acceptance:

- `tasks check --merge` refuses unaudited deliverable edits on a spec created on
  its own branch.
- Replacing an audited clause with an untagged new clause requires a new audit.
- `tasks spec amend` no longer appends a full duplicate deliverable body as a
  parseable second source of proof clauses.

### Slice 3 - Executable Proof Targets

Files to read first:

- `scripts/lib/specDoc.ts`
- `scripts/lib/mergeGate.ts`
- `scripts/tasks.ts`
- `scripts/tasks.test.ts`
- `package.json`

Instructions:

- Write tests first for proof target parsing and merge-gate execution.
- Support clause metadata directly under a proof bullet:

  ```md
  - [c1] The authored ability value is spent at its authored scale.
    proof: vitest src/runtime/contest.test.ts "spends the authored ability at its authored scale"
  ```

- Also support a command target for aggregate proof:

  ```md
  - [c8] The standard gates pass.
    proof: command npm test
  ```

- The merge gate should run only named proof targets, not the full suite by
  default, and fail if a target is missing, skipped, or exits non-zero.
- Preserve optionality. A clause without a proof target is still allowed, but an
  auditor prompt must call out that it requires human verification.

Acceptance:

- A renamed or skipped Vitest test fails the merge gate for the clause that
  names it.
- A failing command proof fails the merge gate and prints the clause id.
- Existing specs without proof metadata still parse.

### Slice 4 - Task Lifecycle Anchors

Files to read first:

- `scripts/lib/taskStore.ts`
- `scripts/lib/taskStore.test.ts`
- `scripts/tasks.ts`
- `scripts/tasks.test.ts`

Instructions:

- Write tests first for `tasks start`, `tasks stop`, `tasks next`, `tasks done`,
  and `tasks check` around in-flight and closed tasks.
- Add `in-progress` to the state model. `tasks next` should skip in-progress
  tasks by default and show the next open unblocked task; `tasks list --state
  in-progress` and `tasks spec show` should expose them.
- `tasks start <id>` transitions `open -> in-progress`, refuses blocked tasks,
  and records enough lightweight metadata to show who/when if the model already
  has a place for it. Do not invent identity plumbing if it would be brittle.
- `tasks stop <id>` transitions `in-progress -> open`.
- `tasks done <id>` accepts `open` or `in-progress`, records `closed` and a
  reachable closing commit. If the commit cannot be known before the commit is
  created, use a follow-up `tasks close-commit <id> <sha>` or infer from the
  latest commit that touched relevant files, but make the mechanism explicit and
  testable.
- Warn after state-changing writes when `docs/tasks.jsonl` has uncommitted
  changes. `tasks check` should distinguish committed store state from
  working-tree-only state where possible.

Acceptance:

- A worker can claim work before implementing it, and a planner can see it.
- A reverted `done` mark is detectable because either the state is absent from
  the committed store or its closing commit is unreachable.
- `requires` remains the only dependency edge; no reverse edge is stored.

### Slice 5 - CLI and Handoff UX

Files to read first:

- `scripts/tasks.ts`
- `scripts/tasks.test.ts`
- `scripts/lib/taskStore.ts`
- `scripts/lib/commitContract.ts`
- `.claude/hooks/commit-msg`

Instructions:

- Write tests first for each user-visible command behavior.
- Add real help: `tasks --help`, `tasks help`, and command-specific help should
  print usage without an "unknown command" error.
- Make `tasks spec <slug>` an alias for `tasks spec show <slug>`.
- Add `tasks spec show --order` using a topological sort over `requires`, with
  cycles still reported by `tasks check`.
- Make `tasks next` concise by default: id, title, system, severity, blockers,
  files, and one-line evidence/deliverable preview. Add `--full` for current
  full evidence behavior.
- Make `tasks search <term>` print which field matched. Do not add a `tags`
  field in this branch unless the implementation needs it for another accepted
  clause; spec membership remains the curated bundle mechanism for now.
- Fix the handoff empty-scan wording and missing-base behavior so the tool never
  claims it proved no branch-local `Next:` when it merely hit a scan cap or
  could not find a merge-base.
- Change the commit hook and `check-commit-msg` so the body is mandatory and
  `Next:` is optional. The error text should point users to `tasks handoff` /
  `tasks next` for resumability.
- Update `.claude/hooks/commit-msg` to call
  `node node_modules/tsx/dist/cli.mjs scripts/tasks.ts check-commit-msg ...`
  when present, with `npx tsx` as fallback.

Acceptance:

- The three questions in this spec are reflected in command behavior and test
  expectations.
- `tasks handoff` is useful without a `Next:` trailer.
- The hook is faster locally without weakening the body requirement.

### Slice 6 - Auditor Prompt and Standard Gates

Files to read first:

- `scripts/tasks.ts`
- `scripts/tasks.test.ts`
- `scripts/lib/specDoc.ts`
- `tsconfig.json`
- `tsconfig.node.json`

Instructions:

- Write tests first for `tasks audit-prompt <spec>`.
- The prompt must include the spec path, branch, merge-base/head range, proof
  clauses, proof targets, current member tasks with files, latest audit pass
  summary, and the recommended mutation-testing language from this spec.
- For pure logic/API clauses, the prompt should explicitly ask the auditor to
  perturb the behavior under review and confirm the named proof fails. For UI
  clauses, it should ask for behavior inspection plus post-implementation smoke
  coverage.
- Enable `noUnusedLocals` and `noUnusedParameters` in the relevant TypeScript
  configs. Fix the dead imports/locals it reveals without broad refactors.
- Remove `lastAuditDoc` only if the files are already touched for prompt/gate
  work and the tests make the removal unambiguous.

Acceptance:

- An auditor can paste the generated prompt into a fresh agent and get the
  expected audit shape without knowing the branch history.
- The unused-local gate catches the class of missing-proof bug observed in
  `combat-continuation-runtime`.
