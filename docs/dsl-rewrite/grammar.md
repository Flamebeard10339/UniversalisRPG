# Content DSL — grammar reference

This is the reference for content authors: how to write `# item`, `# stat`, `# skill`,
`# location`, `# entity`, `# dialogue`, and `# test` sections. It is generated by
reading the parsers (`src/game/contentDsl/*.ts`) as ground truth — every example
below has been checked against the actual grammar, not the design docs that
preceded it. Where the design intent (`.planning/dialogue-strawman.md`) reaches
further than the parser currently does, that's called out under
[Not yet supported](#not-yet-supported).

## 1. Model

Text is the single canonical form of content. A `.dsl` file is parsed into plain
objects and **never regenerated** — there is no printer, and there won't be a
general one; a future structured editor would emit DSL only for the specific
shapes it edits. Treat the file as the source of truth you hand-edit, not as a
save format a tool round-trips for you.

You write only what differs from the default. Most fields have a default —
often derived from the id (`title` humanizes `cooked-shrimp` to "Cooked
Shrimp") or from another field (an item's `examine` defaults to a sentence
built from its `title`). Defaults are filled in at **load time** ("hydration"),
not while you're authoring, so an unauthored field and one you left empty look
identical to the parser: **absent and empty are the same thing**. Writing
`x: ` with nothing after the colon is exactly like not writing `x:` at all.

## 2. File & section structure

### Headings, ids, and comments

A section starts with a heading line:

```
# item cooked-shrimp
```

`# <kind> <id>` — kind and id are both lowercase-kebab tokens (`[a-z][a-z0-9-]*`).
Everything until the next heading (or end of file) is that section's body.
A blank line does not start a new section by itself — you need another `#` line.

A line whose first non-whitespace characters are `//` is a comment and is
ignored completely, at any indentation, including before the first section:

```
// front door — thieving-route entry point
# entity front-door
examine: A heavy wooden door, bound in iron.
```

### Fields

Inside a section body, most lines are `key: value`:

```
# item cooked-shrimp
examine: A simple meal.
```

Multiple fields can share a line, separated by commas:

```
# location loft
x: 0, y: 0, z: 1
```

### Indentation and blocks

A field can take its value from an indented block instead of inline, for any
field whose value is a list (adjacency, entities, tags, an entity's actions,
a dialogue node's beats):

```
# location guide-house
x: 0, y: 0
starting
adjacent:
  beach while front-door.unlocked
entities:
  miki, stairs-up, front-door, dresser, bookshelf, painting, mirror
```

Indentation is whitespace-sensitive and stacks arbitrarily deep — a block's
own lines can themselves carry indented children (an entity action's `on
success:` is a block inside a block; a dialogue choice's effects are a block
under a `->` line). Only list-shaped fields accept the block form; writing an
indented block under a plain scalar field (like `title:`) is an error.

### Free text is line-terminal

Fields typed as free text (`title`, `examine`, dialogue beats, `say:`) consume
the **entire rest of the line**, commas included. This is deliberate — the
comma-splitting that lets you pack `x: 0, y: 0` on one line stops the instant
a free-text field starts, so prose is never mistaken for more fields:

```
# location beach
x: 1, y: 0
title: Sunny, warm, x: 9
```

Here `title` is `"Sunny, warm, x: 9"` verbatim — the trailing `x: 9` is text,
not a redefinition of `x`.

### Flags, bare fields, and bare clause lists

Some fields are a lone keyword rather than `key: value` — a **flag**, true
when the word appears, false (filled in at hydration) otherwise. Location's
`starting` is the only current example:

```
# location guide-house
x: 0, y: 0
starting
```

A kind can also designate exactly one field **bare** — parsed directly, with
no leading key at all, when nothing else on the line matches. Location does
this for a relative position (see [location](#location) below):

```
# location dock
east of bridge
```

And a kind can designate one list field as its **bare clause list**: tokens
that don't match any recognized key are parsed as elements and appended to
it. Item does this for `tags`, and — unlike an ordinary list field — it is
written with **no label at all**:

```
# item cooked-shrimp
examine: A simple meal.
food, +3 regeneration, 60s
```

Writing an explicit `tags: food, +3 regeneration` label currently throws
("unrecognized tag clause") rather than working as an alternate spelling —
the same is true of writing `relative: east of bridge` for location's bare
field instead of the label-less form. Both fields must be written bare; see
[Notes for reconciliation](#notes-for-reconciliation).

### Dynamic entries

Entity is the one kind whose body is mostly **entries**: any `<label>:` that
isn't one of the fixed fields (`title`, `examine`) becomes one action, keyed
by that label. The label may contain spaces (`pick lock:`, `look through:`),
since the label grammar only requires it end in a colon.

### Defaults and hydration

What you write is the **authored** form — a partial object with only the
fields you set. Loading fills in the rest ("hydration"): a default can be a
constant or a function of the object's own id or other fields, resolved
lazily and cached, with a load-time error if two defaults refer to each other
in a cycle. You never need to write a value that equals its default.

## 3. Shared constructs

### References

A dotted path of lowercase-kebab segments: `bridge-open`, `front-door.unlocked`,
`tutorial.quest-given`, `toll.visits`, `player.name`. These name state — world
flags, nested object properties, or (by convention, not special parser
support) a dialogue node's visit counter.

### Conditions

Used anywhere a `when:`/`requires:`/`hidden if:` grammar is documented below.

- A bare reference is truthy-check: `front-door.unlocked`
- Numeric comparison: `stat.attack > 10`, `toll.visits >= 5`. Operators are
  `>`, `<`, `>=`, `<=`, `=`. The right-hand side must be a number.
- `not <condition>` negates.
- `<a> and <b>`, `<a> or <b>` combine (left-to-right list, no parentheses;
  `and` binds tighter than `or`).

```
not tutorial.quest-given
toll.visits >= 5
active-interaction and combat-interaction
```

### Action results

The verbs available anywhere an effect fires — an entity action's results,
`on success:`, a dialogue beat/effect, a choice's indented effects:

| Verb | Form | Notes |
|---|---|---|
| `say:` | `say: <text>` | rest of line is free text |
| `set` | `set: <ref>` or `set <ref>` | colon optional |
| `unset` | `unset: <ref>` or `unset <ref>` | colon optional |
| `give:` | `give: [<n>] <item-id>` | amount optional |
| `take:` | `take: [<n>] <item-id>` | amount optional |
| `xp:` | `xp: <skill-id> <n>` | both required |
| `relocate:` | `relocate: <location-id>` | |
| `discover:` | `discover: <location-id>` | |
| `open modal:` | `open modal: <modal-id>` | two words, one verb |

Several results can share a line, comma-separated:

```
ascend: relocate: guide-house-upstairs, say: You climb the stairs.
```

```
give: 12 coins
take: 5 cooked-shrimp
xp: thieving 4
```

### Tag clauses

A comma-separated micro-grammar, disambiguated by shape (never by keyword
lookup), used for item tags and for an entity action's modifiers:

- a bare word → keyword: `mainhand`, `once`, `food`
- `+<n>[%] <stat-id>` or `-<n>[%] <stat-id>` → a stat bonus: `+3 regeneration`, `+2% attack`
- `<n>m<n>s` (either half optional) → a duration: `4s`, `1m40s`, `1m`

```
food, +3 regeneration, 60s
once, 4s
```

## 4. Kinds

### item

```
item:
  title: text, defaults to the id humanized
  examine: text, defaults to "This is an <title>."
  tags: bare clause list (tag clauses)
```

```
# item cooked-shrimp
examine: A simple meal.
food, +3 regeneration, 60s
```

`title` defaults to `Cooked Shrimp`. `examine`, if you omit it, defaults to a
sentence built from the (possibly also-defaulted) title — literally `This is
an <Title>.`, article and all, regardless of the title's first letter; write
your own `examine:` to control the wording.

### stat

```
stat:
  title: text, defaults to the id humanized
  base: number, defaults to 0
```

```
# stat attack
base: 10

# stat regeneration
```

### skill

```
skill:
  title: text, defaults to the id humanized
  stat-id: text, no default (stays absent if unset)
```

```
# skill thieving
stat-id: attack

# skill mining
```

`mining` above ends up with an undefined `stat-id` after hydration — unlike
`title`, this field simply has no default.

### location

```
location:
  x, y, z: number, each defaults to 0
  title: text, defaults to the id humanized
  examine: text, no default
  entities: list of entity ids
  adjacent: list of "<location-id>[ while <condition>]"
  relative: bare field "<direction> of <location-id>", direction is
            north/south/east/west/up/down
  starting: flag
exclusive: {x, y, z} vs {relative} — set one or the other, never both
```

Absolute coordinates:

```
# location guide-house
x: 0, y: 0
starting
adjacent:
  beach while front-door.unlocked
entities:
  miki, stairs-up, front-door, dresser, bookshelf, painting, mirror
```

Relative position instead of coordinates — written bare, no leading key:

```
# location dock
east of bridge
```

Setting both is an error: `x: 0, y: 0` together with `east of bridge` on the
same section throws "cannot both be set". `adjacent` entries are directional
and one-way — an edge back from `beach` to `guide-house` needs its own line on
`beach`'s section. A travel edge with no `while <condition>` is unconditional;
one that only ever gets used for multi-step pathfinding (no cost/reward of its
own) is still written the same way — that distinction is a matter of how the
edge is used at runtime, not separate grammar.

### entity

```
entity:
  title: text, defaults to the id humanized
  examine: text, no default
  <label>: entries — everything else, keyed by label — become actions
```

Each entry is one action, whose label may contain spaces. Inline form is
results only:

```
# entity stairs-up
title: Stairs
ascend: relocate: guide-house-upstairs, say: You climb the stairs.
```

Block form additionally accepts modifiers, in any order, each at most once:

```
# entity front-door
examine: A heavy wooden door, bound in iron.
pick lock:
  requires: lockpick
  hidden if: unlocked
  once, 4s
  xp: thieving 4
  on success:
    set: unlocked
    say: The lock clicks open.
```

- `requires:` (or `require:`, same meaning) — condition; action unusable if false.
- `hidden if:` — condition; action not even shown if true.
- bare clause lines (not a result verb) are tag clauses — `once, 4s` above
  marks the action single-use with a 4-second duration.
- any result-verb line becomes part of `results`, fired when the action runs.
- `on success:` — a further list of results (inline or as its own block),
  fired only if the action's own results succeeded.

An "enemy-shaped" action (one with a `requires:`/combat-flavored tags) and an
instant action (a bare `results` list with no modifiers) are both just
entities — the design distinction between them is intentional at the content
level, not a grammar-level one.

### dialogue

```
dialogue:
  owner = <entity-id>      (top level, default speaker)
  node <name>:             (one per node)
    when: <condition>       nodes with no when: are internal, goto-only
    once                     bare flag
    sticky                   bare flag
    again: <text>            shown instead of beats on a later visit
    <plain line>             a spoken beat
    goto <node-name>         jump
    -> <text>[  (when <condition>)]
      goto <node-name>        indented under a choice
      <result line>           and/or effects, one per line
```

`owner = miki` sets the default speaker for every beat in the section. A
`talk` enters the **last** node (top-to-bottom) whose `when:` currently holds
— this is the resume mechanism; there's no saved cursor. A node with no
`when:` is unreachable except by an explicit `goto`.

```
# dialogue miki
owner = miki

node greeting:
  when: not tutorial.quest-given
  Greetings, adventurer!
  What do you say I show you the ropes?
  set: tutorial.quest-given
  -> Sounds good.
  -> I'd rather not.
    set: tutorial.snubbed
    goto snub

node remind-mirror:
  when: tutorial.quest-given
  sticky
  again: The mirror is still waiting.
  The mirror awaits you.

node snub:
  Hmph. Suit yourself.
```

Consecutive `->` lines form one menu; a plain line, `goto`, or the next
metadata line closes the menu and continues the node. A choice's indented
children are `goto <target>` and/or effect lines (result-verb lines only — no
bare tag clauses inside a choice). Guard a choice with a trailing
`(when <condition>)`:

```
# dialogue troll
owner = bridge-troll

node toll:
  when: toll.visits >= 5
  Pay the toll!
  -> Here, five shrimp.  (when has-shrimp)
    take: 5 cooked-shrimp
    goto paid
```

`toll.visits` above reads the node's own visit counter as an ordinary
condition reference (no special syntax — the engine maintains it, the grammar
just sees a dotted path). `has-shrimp` is an ordinary boolean flag some other
system must set — a dialogue condition cannot itself check an inventory
count (see [Not yet supported](#not-yet-supported)).

Any spoken line (a beat, an `again:`, or a choice's text) can interpolate or
conditionally include text with `{ }`:

```
node greeting:
  There you are — {player.name}, is it?
  {tutorial.snubbed: You already made your choice.}
  Welcome to {location.name}, {player.name}.
```

`{<reference>}` (no colon) interpolates a value. `{<condition>: <text>}` (has
a colon) includes `<text>` only if `<condition>` holds — the condition is the
full condition grammar above, so `{stat.attack > 10: You look strong.}` works,
but see the caveat on string comparisons below.

### test

```
test:
  run: <test-id>                        compose another test
  talk: <entity-id>
  choose: <choice-text>
  use: <obj-kind>.<obj-id>.<action-id>   action-id may contain spaces
  travel: <location-id>
  expect: <condition>
```

Each directive is a single line — an indented line under a directive is a
parse error. The parser accepts this grammar today; there is no runner yet
(see below).

```
# test tutorial-quest-given
run: enter-guide-house
talk: miki
choose: Sounds good.
use: entity.front-door.pick lock
travel: beach
expect: tutorial.quest-given
```

## Not yet supported

The parser stops short of the following, present in `.planning/dialogue-strawman.md`
or otherwise implied by the design but not yet accepted by the code:

- **String/enum comparisons in conditions** — `player.race = elf` is not
  parseable: the `=`/`>`/`<` comparison operators require a numeric
  right-hand side (`number.parse`). A condition like
  `{player.race = elf: ...}` from the strawman will throw today.
- **Item-count predicates** — there's no `has 5 shrimp`-style condition. The
  troll toll's `(when has-shrimp)` in the worked example is an ordinary
  boolean flag, not a live inventory check; something else must set it.
- **A quest `start:` verb** — the action-result grammar has no `start:`; the
  strawman's `start: escape-island` isn't representable yet. Quest/stage
  state is, for now, plain flags read by ordinary conditions.
- **`# test` execution** — the grammar above parses; there's no runner that
  executes a parsed `Test` against the engine yet.

## Notes for reconciliation

- The strawman's `[label]` explicit jump target (for reconvergence outside a
  choice) doesn't exist in the parser — only `goto <node-name>` (a whole
  node) is supported, not a mid-node label.
- The strawman shows quest effects (`start:`) and inventory-count guards
  (`has 5 cooked-shrimp`) as already-integrated; both are still open, per
  above.
- Everything else checked — node resume semantics, `once`/`sticky`/`again`,
  `owner =`, comma-packed fields, the `x/y/z` vs relative-position exclusivity,
  tag-clause shape dispatch, `require`/`requires` aliasing — matched the
  strawman's intent exactly against the current parser.
- `tags` (item) and `relative` (location) are declared as fields *and*
  designated bare (`clauses: 'tags'` / `bare: 'relative'`), so they are authored
  **only** in their bare form. Writing the labelled form — `tags: food` or
  `relative: east of bridge` — falls through to the bare parser and throws a
  confusing error (`unrecognized tag clause: "tags: food"` / `expected a
  direction`). This is **by design**: bare authoring is the intended form (an
  explicit `tags:` field was deliberately rejected in the phase-0 design), and
  the field declaration is not dead — the engine reads it for the clause-element
  parser and the field's default. The only genuine wart is the error message
  for the mistaken labelled form (it could say "write `tags` as a bare clause
  list"); a low-priority parser polish, not a doc issue.
