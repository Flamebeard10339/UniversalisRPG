# Runtime audit — 2026-07-30

Independent audit of repository system 2 (**Runtime**, `src/runtime`) at `d7c6493`, covering the
15 commits since `83d81d2` — the namespace/flag series `0d984a6`…`d0678d5`, the save-hardening
series `5f3708d`…`b0d6b48`, the resolver changes `b52f629`/`9922073`/`a6b873f`, and the integer
conversion `2c2ccee` + `f9dfd72` that dominates the window.

Baseline: `npx tsc --noEmit` clean, **509 tests / 33 files** green.

Every finding below was reproduced against a throwaway fixture or a mutation, described inline so
it can be re-run. The prior audit's open items (pass-1 L4 and L6, both BLOCKED on the
`action.health`/`target:` unification) are not re-reported, but M2 is fresh measured evidence for
exactly that unification and should be read as raising its priority.

## What the integer conversion got right

Stated first because it bounds everything else: **the conversion did not break associativity, and
the remainder design is sound.** I fuzzed a pool whose rate changes sign mid-span — filling to the
ceiling under a buff, then draining once it expires — against every split point at 137 ms
intervals across a 120 s horizon, comparing both the level and the carried remainder. All 875
splits agreed with the one-shot resolve, including the splits that land inside the clamped region
where `setPoolLevel` discards the remainder.

I also checked the arithmetic the conversion rests on. `state.resources`, `state.time`, every
cadence `progress`, `healthRemaining`, and `resourceRateRemainders` are closed under the
operations that write them: every rate, max, delta and damage reaches them through `toMilliUnits`
or `secondsToMs` (both `Math.round`), `divideRateRemainder` returns integers by construction, and
`msUntilEmpty`'s `- 1` is the correct strictness constant for `floor(acc/60000) <= -current`.
`advanceTime` and `resolve` both reject a non-integer at the seam. The scale holds.

`msUntilEmpty` is also safe against the one degenerate input it can receive: a rate small enough
that `toMilliUnits` rounds it to `-0` divides to `+Infinity`, which loses the comparison against
`boundary` rather than producing a bogus one. That is luck rather than design, but it holds.

## H1 — `checkSave` never looks inside the three fields that have an inside, and `loadSave` crashes on them with a `TypeError`

**Verified, two reproductions.** `save.ts:38-52` gives every save field a `holds` predicate. For
the ten scalar- and number-shaped fields it is a real check. For the three object-shaped fields —
`activeAction`, `player`, `activeBuffs` — it is `isObject`, which is to say no check at all. Those
are exactly the three fields with internal structure to get wrong.

The rule the file states for itself (`save.ts:28-29`):

> "A `# save` body is hand-written JSON that nothing else checks, so this is where a
> `"time":"potato"` is caught."

It catches `"time":"potato"` and misses the class that actually crashes:

| `# save` body (version 5) | Result |
| --- | --- |
| `{"time":"potato"}` | `RuntimeError: save field time holds "potato"…` ✅ |
| `{"activeAction":[]}` | `RuntimeError: …not what activeAction keeps` ✅ |
| `{"activeAction":{}}` | **`TypeError: Cannot read properties of undefined (reading 'indexOf')`** |
| `{"activeAction":{"ownerRef":"entity.oven","actionLabel":"bake","repeating":false,"healthRemaining":1000}}` | **`TypeError: Cannot convert undefined or null to object`** |
| `{"player":{}}` | accepted; `state.player.name` is `undefined` thereafter |
| `{"activeBuffs":{"k":{}}}` | accepted, then silently pruned as "its stat undefined is not loaded" |

The first crash is `parseOwnerRef` (`save.ts:115`) on an absent `ownerRef`. The second is the
interesting one: **every id in that body is real.** The owner exists, the action label exists, so
`activeActionProblem` has nothing to prune and reaches `Object.keys(active.cadences)`
(`save.ts:127`) on an absent `cadences`. Nothing downstream can recover, because the crash is
inside the validator.

That the intent was the opposite is explicit two lines earlier: `activeActionProblem` wraps
`findActionOwner` in a `try/catch` that converts a `RuntimeError` into a warning and rethrows
anything else (`save.ts:119-122`). The author was thinking about precisely this conversion and it
is defeated by the next statement. A validator that throws a raw `TypeError` on the input class it
exists to validate has not validated it — and this is the only gate between hand-written JSON and
the resolver, since `06c2e47` routed `pruneStateForRegistry` through it for browser and disk saves
too (`scripts/play-cli.ts:320`).

**Fix**: `holds` for these three needs to be a real structural predicate, not `isObject` — for
`activeAction`, at minimum a string `ownerRef`, a string `actionLabel`, and a `cadences` object
carrying `PLAYER`. That is the same shape `activeActionProblem` already assumes; it just has to be
asserted before the assumptions are used rather than after.

## M1 — the `# test` regressions cannot see the largest change in the window

**Verified by mutation.** I dropped `toMilliUnits` from `initResources` (`effects.ts:81`), so
every pool initialises at 1/1000 of its intended level, and ran the shipped content:

```
✓ test "tutorial-island.tutorial-quest-given" passes
✓ test "tutorial-island.miki-route-full" passes
✓ test "tutorial-island.save-restores-object-owned-flags" passes
× tutorial-island health resource (Pass 2 end-to-end) …
```

All three `# test` sections pass with every pool off by 1000×, including `miki-route-full`, whose
`expect: miki-route-end` compares the whole save diff. The only thing that fails is a hand-written
TypeScript assertion at `integration.test.ts:40`.

The cause is in the fixture `2c2ccee` migrated. `miki-route-end` carries
`"resources":{"tutorial-island.health":0}` — zero is the single value invariant under a scale
change, so rescaling it was a no-op and the fixture pins nothing about the new scale. `time` was
rescaled `107.2` → `107200` and *does* discriminate, which is why a seconds/milliseconds mixup
would be caught and a units/milli-units one would not.

CLAUDE.md designates `# test` sections as *the* regression format. For the largest change in this
window that format certified nothing, and the mechanism — a fixture whose only pool value is the
one value the transformation fixes — will recur on the next scale change unless a fixture pins a
pool mid-range.

## M2 — `ability:` means two different numbers depending on which fight path reads it

**Verified.** One module, one stat `blow` at `2.5`, two actions differing only in `health:` vs
`target: health`. Four attempts each, starting from 100:

```
healthless (deterministic) path:  100000 -> 90000   = 2.5 per attempt
target:    (stochastic)   path:  100000 -> 92000   = 2.0 per attempt
```

A 20% difference from the same authored number. The deterministic path takes
`toMilliUnits(statValue(action.ability))` (`runtime.ts:72`) and is exact; the stochastic path goes
through `hitDamage`, which is `Math.max(minDamage, Math.trunc(attack - dr))` (`stats.ts:47`) and
quantises to whole units before `damagePool` converts up.

The `Math.trunc` predates this window, so the asymmetry is not new — but the integer conversion
made the healthless path exact while leaving the target path quantised, which widens the gap
rather than closing it, and it is the sort of thing a conversion touching every damage site was
the natural moment to reconcile. This is a measurement for the `action.health`/`target:`
unification that pass-1 L4 and L6 are both blocked on: the two paths do not merely differ in
bookkeeping, they deal different damage.

## M3 — `rng` is the one number in `GameState` the conversion left un-integered, and a fractional cursor collapses the stream

**Verified.** `SAVE_FIELDS` validates `time` and both pool records with `isInteger` and `rng` with
`isNumber` (`save.ts:48-49`). Since the pass-2 H1 fix, `nextRandom` is
`(Math.imul(cursor.rng, MULTIPLIER) + INCREMENT) >>> 0` (`rng.ts:14`), and `Math.imul` applies
`ToInt32` to its arguments. So a save carrying `"rng":0.5` is accepted, and:

```
draws from rng=0.5    : 0.0000028742942959, 0.8275770242, 0.6524071617, 0.8374803169
draws from rng=12345  :                     0.8275770242, 0.6524071617, 0.8374803169
```

Every fractional cursor truncates to the same integer and lands on the same fixed stream one draw
later. Two saves that differ only in their `rng` fraction produce bit-identical futures. The
window's own work makes this worth fixing rather than tolerating: `5f3708d` built `SAVE_FIELDS` as
a `Record` over an exhaustive key type specifically so a field could not be forgotten, and the
table is exhaustive over *names* while remaining loose about *values* — which is the same root as
H1. `rng: isInteger` is a one-word change.

## L1 — `attemptDuration`'s floor gives one authored value three different fates

`Math.floor(timeMs / speed)` (`stats.ts:53`) can now reach 0 for any positive `time:`, which the
pre-conversion float division could not. What happens next depends on which path reads it:

| Path | `duration === 0` |
| --- | --- |
| `armAction`, repeating | `RuntimeError` at arm time (`runtime.ts:404`) |
| `applyDueBoundaries`, deterministic non-repeating | treated as instant and completed (`runtime.ts:315`) |
| `resolveStochasticSegment` | **`RuntimeError` thrown mid-resolve** (`runtime.ts:215`) |

Reproduced for the third row with `time: 1, speed: 2000`: the action arms clean, `useAction`
resolves a zero-length first unit without complaint, and the next `resolve()` that crosses any
span throws `action entity.dummy.poke resolved a non-positive attempt duration (0)`. No load-time
check is possible because `speed` is state-dependent, so the three fates are the whole story.

Unreachable in shipped content — a 60 s action needs a speed stat above 60,000 — which is why this
is LOW rather than higher. It is listed because the divergence is not a decision anyone made; it
is what the floor did to three call sites that each already handled zero their own way.

## L2 — `resourceRateRemainders` is never cleared when a resource stops having a rate

`settlePools` writes the remainder only under `if (snapshot)` (`effects.ts:146`) and `continue`s
past a resource with neither snapshot nor delta (`effects.ts:140`). A remainder accrued while a
buff supplied a rate therefore survives the buff indefinitely and is re-applied if the rate ever
returns. Bounded at one minute's accrual — under one milli-unit — because the resolver forces a
boundary at every rate change, so this is cosmetic in the pool itself. It is visible, though:
`resourceRateRemainders` is a save field, so the stale value is serialised and compared by
`compareSave`, and a `# save` fixture recorded either side of a buff expiry will carry it.

## L3 — `PlaySession.logCursor` no longer carries information, and the one place it could is a nested session

`9922073` made `view()` clear the log outright (`session.ts:192-194`), setting the cursor to 0 on
every read. Every other assignment — `startSession:169`, the `load` directive at `:345`, and
`runTest:369` — can now only produce 0 in a session that has ever called `view()`. The field
survives as a parameter that is always the same value.

The exception is the reason to mention it: `runTest` builds a *second* `PlaySession` over the
caller's state (`session.ts:369`). If that inner session reaches `view()` — a `begin:` directive
does, via `beginAction` — it clears a log the outer session is still holding a cursor into, and
the outer `state.log.slice(session.logCursor)` then silently returns nothing. Unreachable at
today's cursor values, which is exactly what makes it a trap rather than a bug: the invariant that
saves it is "the cursor is always 0", which no name or type records.
